# 옆자리 AI 아키텍처 v2 — 온디바이스 개인화 보정 × 경량 명령 해석

> 핵심 질문: **"범용 음성인식이 틀린 장소 이름을, 개인 데이터를 차 밖으로 보내지 않고 이 운전자에 맞게 바로잡을 수 있는가?"**

## 1. 설계 원칙
1. **음성인식은 Pleos STT SDK로만.** 대회 정책상 차량 마이크 음성은 STT SDK로 처리한다. 옆자리는 STT가 준 텍스트 뒤에서 보정한다. 어떤 음성인식 엔진 위에도 얹을 수 있는 계층이다.
2. **사실은 수첩에, 말 습관은 모델에.** 방문 기록 같은 사실은 모델 가중치에 외우게 하지 않고 차 안 DB에 둔다. 새 장소가 바로 반영되고, 지우라면 즉시 지울 수 있고, 없는 장소를 지어내지 않는다. 명령 해석 모델(LoRA)은 '말을 구조로 바꾸는 법'만 배운다.
3. **틀릴 수 있다는 전제.** 확신도에 따라 바로 실행 / 한 번 확인 / 선택지 3개로 나누고, 되묻기는 시선 앞 HUD와 음성 번호로 끝낸다.
4. **고를수록 배운다.** 사용자의 선택이 곧 학습 데이터다. 가벼운 순위 모델은 차 안에서 즉시 갱신하고, 무거운 모델 갱신은 차가 쉬는 시간(주차·충전)에 한다.
5. **보내는 것은 숫자뿐.** 공용 모델 개선은 연합학습으로 하고, 원본 기록 대신 서명된 가중치 변화량만 보낸다.

## 2. 처리 흐름

```
 운전자 음성 ─▶ Pleos STT SDK (온디바이스) ─▶ "서심다응 가자"
                                                   │
          ┌────────────────────────────────────────┴───────────────────────────────┐
          │ ① 명령 해석 (OnDeviceIntentEngine)                                      │
          │    목표: Qwen3-0.6B + 차량 명령 LoRA (4bit GGUF) / 현재: 규칙 기반 대체물     │
          │    → {intent: NAV_PLACE, place: "서심다응", stop: destination}           │
          └────────────────────────────────────────┬───────────────────────────────┘
                                                   ▼
          ┌──────────────── ② 개인화 보정 엔진 (PersonalBrain, 차 안) ───────────────┐
          │  후보 찾기: 발음 유사도 ≥ 0.55 (자모 단위 가중 편집거리, 부분 정렬)          │
          │  특징 6개: 발음 · 자주(90일) · 시간대 · 거리/경로 · 최근 · 선호(전에 고름)     │
          │  확률 = softmax(w · x)  ← 방문 기록은 AES-256-GCM 암호화 저장소에서만 읽음     │
          └────────────────────────────────────────┬───────────────────────────────┘
                                                   ▼
          ┌──────────────── ③ 확신도 → 행동 ─────────────────────────────────────────┐
          │  p1 ≥ 0.85 & p1−p2 ≥ 0.5 : 바로 실행 + 10초 되돌리기("아니야")              │
          │  p1 ≥ 0.50             : 한 번 확인 "성심당 대전역점으로 갈까요?"             │
          │  그 밖                  : HUD 선택지 최대 3개 → "1번" / "본점" / 터치         │
          └────────────────────────────────────────┬───────────────────────────────┘
                                                   ▼
     ④ NaviHelper.requestRoute / addWaypoint   ⑤ TTS SDK 안내   ⑥ 앞유리 HUD 시뮬레이터
                                                   │
          ┌──────────────── ⑦ 차 안 학습 ────────────────────────────────────────────┐
          │  가중치: w ← w + lr · (x_고른 − Σ p·x)   (조건부 로짓 1스텝, 수 ms)            │
          │  표현 기억: "서심다응" → 성심당 · 선택 기억: 이 말 → 이 지점                    │
          │  기록 사슬: SHA-256 해시 체인 (위·변조 검증)                                  │
          └────────────────────────────────────────┬───────────────────────────────┘
                                                   ▼ (선택 동의 · 주차/충전 중 Wi-Fi)
     ⑧ 연합학습 업데이트: Δw 6개 → 클리핑(‖Δ‖≤1) → 가우시안 잡음(σ=0.05) → SHA-256 → ECDSA P-256 서명
```

Gleo 연동: `GO_TO_MY_PLACE(place, stop_type)` — Gleo가 들은 장소 이름도 ②부터 같은 경로를 탄다.

## 3. 구성 요소

### ① 명령 해석 — `ai/nlu/OnDeviceIntentEngine.kt`
- 목표 모델: **Qwen3-0.6B (Apache-2.0)** + LoRA(r=16, q/k/v/o/gate/up/down). 출력은 JSON 한 줄이다(`ml/README.md`).
- 학습 데이터: 의도 26종 × 템플릿·구어 변형 × 장소 이름 × **음성인식 오타 주입**(Hangul.kt와 같은 혼동 규칙). 테스트에는 학습에 없는 장소 이름과 템플릿을 쓴다.
- 배포: LoRA 병합 → GGUF Q4_K_M(약 0.4GB) → llama.cpp(Android NDK) 또는 NPU. 목표는 300ms 이내다.
- 현재 앱: 같은 출력 구조의 규칙 기반 대체물(`KeywordIntentEngine` + `QueryParser`)이다. 인터페이스가 같아서 모델로 바꿔도 앱 코드는 그대로다.

### ② 개인화 보정 엔진 — `ai/personal/`
| 파일 | 역할 |
|---|---|
| `Hangul.kt` | 자모 분해 + 받침 대표음 + 혼동 자모 가중치(ㅐ/ㅔ 0.2, ㅓ/ㅗ 0.5, ㄱ/ㅋ/ㄲ 0.4, ㅡ·받침 ㅇ 삽입·삭제 0.5 …) + 부분 정렬 편집거리 |
| `QueryParser.kt` | 장소 명령·되묻기 대답(응/아니야/2번/본점/취소) 해석 |
| `PersonalBrain.kt` | 후보 생성, 특징 6개, softmax, 확신도 단계, 학습(가중치·표현·선택 기억) |
| `PersonaFactory.kt` | 가상 운전자 '서준'의 장소 21곳 + 90일 방문 기록(합성, 고정 seed) |
| `PrivacyLedger.kt` | 해시 체인, 연합학습 업데이트 묶음(클리핑·잡음·해시·서명) |
| `PersonalService.kt` | 엔진 + 암호화 저장(`platform/secure/SecureVault.kt`: AES-256-GCM·ECDSA, Android Keystore) |

**왜 이 특징들인가**: P(장소 | 들린 말, 나, 지금) ∝ P(들린 말 | 장소) × P(장소 | 나, 지금). 앞의 항은 발음 유사도, 뒤의 항은 개인 기록(자주·시간대·거리·최근·선호)이다. 발음 항이 없으면 무슨 말을 해도 자주 가는 곳으로 끌려가고, 개인 항이 없으면 같은 브랜드 지점들을 구분하지 못한다.

### ③~⑥ 대화·HUD — `YeopjariStore.kt`, `ui/components/HudView.kt`, `ui/screens/PersonalScreen.kt`
- 되묻기 상태: `Clarify(stage = CONFIRM | CHOOSE | UNDO, options ≤ 3)`. HUD와 화면이 같은 상태를 본다.
- 주행 중(CarUxRestrictions)에는 HUD와 큰 버튼 3개만 보이고, 분석 패널은 숨긴다.
- HUD는 공개 SDK에 그리기 API가 없어 앱 안 시뮬레이터로 재현한다. 정보 구조(질문 1줄 / 후보 3개 / 학습 알림)는 실차 HUD에 그대로 옮길 수 있다.

### ⑦~⑧ 학습·개인정보
- 차 안 즉시 학습: 순위 가중치 6개(경사 상승 1스텝), 표현·선택 기억. 저장은 암호화 금고에만 한다.
- 연합학습: 서버는 여러 차의 서명된 Δw를 평균해 기본 가중치·지역 사전을 개선한다. 원본 방문 기록·좌표·시각·음성은 받지 않는다.
- 블록체인 기술 중 **개인키 서명**과 **해시 체인**만 쓴다. 분산 원장은 쓰지 않는다. 지울 수 없는 공개 원장은 개인정보 삭제권과 충돌하기 때문이다.
- 서버 측 원본 학습이 꼭 필요한 확장 기능이 생기면 기밀 컴퓨팅(TEE, GPU 기밀 연산)으로 처리한다. 운영자도 복호화된 데이터를 볼 수 없게 하는 방식으로 설계한다.

## 4. 평가
- `app/src/test/.../PersonalEvalTest.kt`: **실제 앱 엔진 코드**를 JVM에서 돌린다. 가상 운전자의 미래 4주 방문을 정답으로 두고, 브랜드 이름·음성인식 오류 이름·종류어 질의를 만든다. 일반 검색 / 발음 보정만 / 발음+개인 기록 / +차 안 학습을 비교하고, Top-1·Top-3·자동 실행률·잘못된 자동 실행률·되묻기율을 측정한다. 결과는 `docs/eval/personal_eval.md`에 있다.
- `ml/eval_nlu.py`: 명령 해석 LoRA의 JSON 정확도, 의도 정확도, 장소 구간 일치율(잡음/깨끗 분리), 지연 시간을 측정한다.

## 5. 성능·자원
- 보정 엔진: 장소 수백 곳 기준 1회 수 밀리초(JVM), 메모리 수 MB, 네트워크 0
- 명령 해석 모델: 4bit 0.6B ≈ 0.4GB, 목표 지연 < 300ms(NPU/CPU)
- 주행 중 CPU < 5%: 리스너 우선, 15초 주기 조회, 학습은 선택 순간에만(수 ms)

## 6. 이전 설계(v1)에서 이어지는 부분
- 하이브리드 구조(온디바이스 우선, 복잡한 계획만 자체 추론 LLM), 안전 규칙 엔진, 컨텍스트 엔진(충전·졸음·펫·뒷좌석 등)은 그대로 유지한다. v2는 그 위에 '이 사람을 아는' 개인화 계층을 핵심으로 세웠다.
